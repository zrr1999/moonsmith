## 已确认的方向

构建失败继续保留 `Incomplete` / 退出码 3，附独立归约结果；诊断规则由 MoonBit 工具链的
专用 Oracle 定义，复用 Engine 会话。此前决定及调查依据见
[构建异常归约补齐方案](native-release-reduction-plan.md)。

首层实现版本化构造器诊断 Oracle 与协同语言候选。Oracle 同时要求目标诊断及两个成功
控制组，不把 exit 255 直接当作目标身份；候选继续经过完整检查和成本过滤。
本层提供后续装配所需能力，尚不表示 CLI 已自动归约构建异常。

首轮 Ubuntu CI 的真实案例测试返回 `NotPreserved`；同版本 MoonBit 的本机 Clang 识别通过。
用本机 GCC 16.2.0 对已保存的生成 C 做只读语法检查，确认相同未声明构造器报告为
`'_M0L6constrS86' undeclared (first use in this function)`。Oracle 同时识别 Clang 和
GCC 的完整消息模式，GCC 接受配对的直引号和弯引号，仍拒绝其他标识符、附加错误及不完整证据。
真实案例断言附带原始观察，便于继续核对不同平台的诊断；本地 GCC 语法检查不替代 Ubuntu 实测。

## 十月范围纠正与已确认选择

用户明确纠正：参考求值不属于十月计划；等价变换后的正常输出不一致与配置间差分不一致
属于同类；独立版本化记录留待后续，目前本地记录即可。此前把参考求值接入及新归档协议
列为本月阻塞项扩大了范围。当时仅撤销这两项要求、保留未合入求值器的处置，
已由下文 2026-10-24 范围复核纠正。

执行按以下边界推进：

1. 日常生成、差分及构建失败归约不调用参考求值器。构造器诊断的运行接受条件改为当前
   候选的 native debug 与 wasm-gc debug 均成功、产生有效且相同的输出；仍需目标诊断。
   控制组一致不能证明共同结果正确，不能与此前人工调查的参考值确认混称为同一证据强度。
2. 等价变换观察按同一观察协议参与差分；有效结果不一致返回 2，缺失或失败且无有效分歧
   返回 3。构建失败本身仍为 `Incomplete`，不冒充正常输出差异。
3. 复用原始案例和追加式执行记录。新增关联、判据及搜索结果先写本地 Markdown 记录，
   不新增版本化归档格式、迁移协议或跨版本读取保证。
4. Host 仍遵循下述正式依赖规则；未获原生 POSIX 实现授权，不改换执行器。

实现分层：先在 #39 顶部接入构建失败自动归约及本地记录，再接入等价变换差分。
验收使用小规模固定输入、真实三例诊断及反例，不重复 10,000 样本实验。

## Host 依赖核对

当前依赖 `moonbitlang/async@0.22.4`。上游最新正式
[v0.22.5](https://github.com/moonbitlang/async/releases/tag/v0.22.5) 发布于 2026-10-14；
该 tag 的树为 `11749dec32e2b4de8cc8a6101e18110019c29893`。
[公开 process API](https://github.com/moonbitlang/async/blob/v0.22.5/src/process/pkg.generated.mbti)
没有进程组隔离参数；
[取消实现](https://github.com/moonbitlang/async/blob/v0.22.5/src/process/unix.c)使用
`kill(pid, signal)` / `kill(pid, SIGKILL)`，针对单个进程。
因此仅升级该正式版不能证明进程树隔离与后代清理已经实现。

仓库要求外部依赖新增能力先经上游实现与评审、正式发布，再升级适配；未获路线调整授权前，
不引入私有补丁、临时启动脚本或另一套旁路执行器。
