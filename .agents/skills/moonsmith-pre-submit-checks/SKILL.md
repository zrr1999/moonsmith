# MoonSmith 交付检查

以当前改动和实际证据判断是否达到用户指定的交付终点；执行现有授权，不另设例行确认步骤。

## 核对交付范围

读取当前任务授权、适用的仓库约定、[贡献指南](../../../CONTRIBUTING.md)和现有 Git 状态。
核对 staged、unstaged、相关未跟踪文件及任务涉及的提交范围，区分已有工作与本次改动。
保护无关内容，不用全量暂存把其他任务的代码、运行产物或本机状态混入交付。

按[贡献指南](../../../CONTRIBUTING.md#zendev-skill)检测 ZenDev 的 `evolution` 演进记录 skill；
缺失时推荐安装，不将安装变成交付门禁。

按 [FP-0000](../../../fps/FP-0000-governance.md)核对提案门槛：
仅对已有设计未覆盖且有明确大影响面的新决定要求 FP。文档纠错、恢复预期行为的意外
bug 修复和既定设计的实现直接检查对应证据，不为了补齐清单而创建新提案。

公共行为变化需同步权威架构文档与行为测试；只有产品方向发生变化时才按贡献指南维护演进记录。
检查链接指向的契约是否存在，设计状态是否仍与实现一致；不维护第二份命令表或架构事实源。

## 选择并完成检查

按贡献指南和当前任务配置选择检查，先确认验证对象与改动对应：文档执行文档门禁，
实现执行相关行为测试及构建检查，入口变化验证实际入口。普通文档改动不要求新增产品测试。

未跟踪文件不会自动进入全仓文件检查，使用贡献指南中的定向文件检查将其覆盖；
不要为了检查改变无关文件的暂存状态。检查完成后重看 diff，确认没有意外格式化或生成内容。

将验收条件逐项对应到代码或执行证据，记录实际命令、结果和未执行范围。工具缺失、依赖安装
失败、测试失败、跳过和零项测试分别说明；继续能独立完成的检查，不将环境问题伪装成代码结论。
涉及工具链实验时记录版本、配置和原始记录位置，不把骨架类型检查当作产品或多后端验收。

检查通过后停止重复验证；只有新修改、失败或尚未解决的具体疑点才扩大检查范围。
缺少必需证据时说明具体缺口和下一步，不把“未执行”写成“通过”。

## 按授权交付

只有当前终点包含提交或 PR 时，才核对贡献指南中的英文标题、emoji 与 type 规范，以及
[PR 模板](../../../.github/pull_request_template.md)。保留真实验证结果，不因起草消息扩大交付范围。

已有 PR 属于任务范围时，读取其当前 head、base 及检查对应的修订；旧提交的绿色结果不能代表
当前 head。把本地检查、远端 CI、评审状态及尚待验收的产品行为分别报告，pending 仍是 pending。
仅本地交付不需要为完成检查而创建远端对象。

给出本次改动范围、已执行检查、验收证据、剩余限制和实际达到的终点。提交、推送、创建 PR、
合并与发布各自遵循当前任务明确授权；skill 的加载不会新增权限，也不要求重复确认已有授权。
