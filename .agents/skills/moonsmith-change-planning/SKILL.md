# MoonSmith 变更规划

从当前实现与用户目标确定要改变的行为，让后续实现能按明确的责任边界和验收标准推进。

## 核实问题与责任

阅读 [README](../../../README.md)、[仓库协作约定](../../../AGENTS.md)、受影响源码和邻近测试。
沿 README 和[贡献指南](../../../CONTRIBUTING.md)的链接读取相关架构、语义或依赖文档，核对
责任边界与验证入口；只引用目标分支实际存在的资料。区分已实现行为、拟定契约与实测证据；
架构草图中的类型、子包和命令不能直接当作现有 API。包为空时明确尚缺实现与行为基线。

沿调用方、被调用方和应用装配入口追踪改动，确定状态、决策及副作用各自的唯一责任方。
Core 拥有编排、判定和搜索，语言适配器拥有程序语义及候选，Host 拥有进程和文件系统；
新增数据与接口应服务于实际跨边界交互，避免让 Core 依赖具体语言 AST 或 Host。

新增语言构造需沿程序表示、合法性检查、生成、求值、源码输出及归约候选逐项核对影响，
并明确适用的 profile。涉及 Host 或外部库时，核对仓库实际采用的依赖及当前 API，
区分基础操作验证与完整进程生命周期的验收。

## 判断是否需要提案

按 [FP-0000](../../../fps/FP-0000-governance.md)，只有现有设计未覆盖的新决定，且有明确的
大影响面，才要求新 FP。说明谁依赖现有保证、
保证如何改变，以及实际的迁移、协调或恢复成本；新增接口、跨包修改或代码量本身不够。
文档纠错、修复意外 bug 以恢复预期行为、普通兼容增强和既定设计的实现直接推进，
即使原 bug 后果严重也不因此补提案。没有大影响证据时不以“保险”为由创建 FP。

## 先调研，再询问关键选项

起草新提案或实质修订方案前，必须先调研当前实现、已有决定和可行替代，再向用户询问
尚未确认的关键选项。提案请求本身不代表用户已选定方案，也不能等完整方案写定后才补问。

- 从源码、测试和相关 FP 取得问题证据。涉及外部方案、依赖或 API 时，核对当前官方文档、
  源码或论文；记录来源及适用版本，区分事实、推断与未验证假设。资料不可得时说明缺口，
  不虚构调研结论；只继续不依赖该证据的部分。
- 围绕会改变范围、可见行为、判定语义、状态归属、兼容迁移或长期成本的取舍列出可行选项。
  适用时包含维持现状，说明推荐项、依据和各项代价；先问会影响后续选择的根问题。
  不把可自行查明的事实交给用户，也不为凑选项提供已知不可行的方案。
- 必须实际提问并取得关键选择，不能仅列出待决问题后自行定案。已有明确选择时引用其依据，
  不重复询问；用户明确委托 agent 决定时，按约束选取并记录委托与理由。
  普通可逆实现细节可自行处理，不能把上述设计取舍降格为细节。
- 等待回答期间可继续独立调研和不依赖答案的草稿，未决部分明确标为待选择。
  无回复不等于同意推荐项；不要把未决选项写成既定结论或推进依赖它的实现。
- 在现有提案模板的相关章节记录调研依据、选择、决定来源、放弃方案的理由与剩余问题，
  不另建状态字段或审批流程。用户选择设计方向不等于提案已采纳、实现或获准发布。

## 形成最小方案

- 将目标写成可观察结果，说明输入、输出、失败边界和不应改变的行为。算法改动明确种子、
  预算及稳定顺序；案例或重放改动明确原始案例与追加式执行记录的关系。
- 比较维持现状与可行方案的责任归属、语义重复、兼容成本和验证难度，推荐满足当前目标的
  最简单方案；按上节取得关键选择后再展开。把相邻清理和未来扩展留在范围外，不预建没有
  真实调用者的接口或包。
- 按依赖安排步骤，先验证最不确定的行为；为每个切片指定所属包、必要文档、行为测试与
  验收证据。最小切片用于组织执行，不缩减用户已要求的最终结果。

## 交付

给出问题证据、选择及理由、受影响边界、实施顺序、验收标准、验证命令和仍待决定的事项。
命令从贡献指南及当前任务入口取得，不把设计文档中的产品命令当作已可运行的入口。
说明每项结论来自源码、已执行检查还是待验证假设；不以空包检查证明生成、归约或多后端能力。

规划不新增执行权限。用户已要求实现时，按此方案继续到当前授权的终点；仅要求设计时交付方案。
